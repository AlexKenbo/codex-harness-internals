# SRC-0015：网络审批、会话缓存与沙箱契约

> 本文是中文模块导读，不是逐字段译本；审批策略名称描述代码行为，并不替代实际权限设置。

## 职责与关键实体

本模块集中描述执行运行时的共同契约：`ToolRuntime` 组合 `Approvable` 与 `Sandboxable`，`SandboxAttempt` 负责构造执行请求，`ExecApprovalRequirement` 表示跳过、请求或禁止审批。`NetworkApprovalService` 跟踪活动调用、调用结果、会话批准/拒绝集合以及待决主机；`ActiveNetworkApproval` 可以即时结束，或转为延迟清理的 `DeferredNetworkApproval`。工具级 `ApprovalStore` 与主机级缓存是两套机制，不应混淆。

实体入口：[结构](../../SRC-0015/structural.json)，精确 ID：`SRC-0015/entity/network-approval-service`、`SRC-0015/entity/host-approval-key`、`SRC-0015/entity/approval-store`。

## 主要规则

主机键由小写 host、protocol、port 三部分构成，审批 ID 形如 `network#{protocol}#{host}#{port}`。拒绝集合优先于允许集合；同一主机键的并发请求只由第一个 owner 发起审批，其他请求等待共享决定。等待者先注册通知再读决定，写入决定后唤醒所有等待者，避免丢通知。

网络审批流程要求存在活动轮次，沙箱策略为 ReadOnly 或 WorkspaceWrite，且审批策略不是 Never。批准一次不等于批准整个会话；会话批准移除对应拒绝键，拒绝型网络策略修订则反向更新。已有 `DeniedByUser` 不能被后续结果覆盖。

工具级缓存只有所有非空 keys 都是 ApprovedForSession 时才命中；空 keys 直接请求决定，不因“全称条件为空”而误认为已批准。仅 ApprovedForSession 写入该缓存。默认执行审批矩阵还区分文件系统是否受限，以及 Granular 是否允许沙箱审批。

核对：[规则](../../SRC-0015/rules.json)中的 `SRC-0015/rule/session-denied-host-precedence`、`SRC-0015/rule/pending-host-approval-deduplication`、`SRC-0015/rule/default-exec-approval-requirement-matrix`、`SRC-0015/rule/with-cached-approval-empty-keys-defense`。

## 用例流程

`SRC-0015/uc.sub/handle-inline-network-policy-request` 规范化目标，先查拒绝、再查批准，创建或加入待决请求，检查策略，将请求路由到 Guardian 或用户，再映射 ReviewDecision、更新缓存并通知等待者。启用受管网络且有代理规格时注册活动审批；即时结束将拒绝转为 ToolError，延迟模式在后台活动结束后注销。详见[用例](../../SRC-0015/use-case.json)。

## 边界与失败处理

没有明确 registration_id 时，只有恰好一个活动调用才能归属拒绝结果。网络策略修订持久化失败会发 Warning，但不撤销已经作出的当前批准或拒绝。注销同时清理活动记录与结果；跨会话同步只替换批准主机，不复制拒绝集合。会话已释放时 decider 返回 ask，而不是虚构批准。审批缓存序列化失败按未命中或不写入处理。沙箱重试、首次绕过与已批准复用分别有独立规则，不能由某个默认值推导出无限制执行权限。

## 阅读提示

阅读审批轨迹时应同时保留目标键、注册标识和决定来源。相同主机但协议或端口不同，不是同一个缓存目标；相同工具涉及多个路径时，也必须逐个满足工具级缓存条件。用户拒绝与策略拒绝的差别会影响最终错误文案和归属，不能只用一个布尔值解释所有失败。
